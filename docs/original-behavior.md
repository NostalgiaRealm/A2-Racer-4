# Original behaviour

What is established about the original A2 Racer 4 - De politie slaat terug! (Davilex, version 1.01, with its two official updates), how it was established, and where the port stands against it. State of 2026-11-01. Evidence per finding is in [`behavior/`](behavior/), status per feature in [feature-parity.md](feature-parity.md), procedures and results in [validation.md](validation.md), programs and versions in [provenance.md](provenance.md), deliberate changes in [intentional-differences.md](intentional-differences.md).

## How to read it

| Word | Meaning |
|---|---|
| Confirmed | Read from the shipped code or data: disassembly, a decompile checked against it, or a parse of the files. It does not mean seen running, see [Limits](#limits-of-the-evidence). "Confirmed in the port" means a trace of the recompiled code, which by itself says nothing about a period machine. "Measured", in the area documents "Confirmed, measured", means read from the running original by reference-wine: a fact about that one setup under Wine, not about Windows or a period machine. On the 8-bit path Confirmed can also mean read from the frames of reference-86box: a fact about that one emulated machine |
| Inferred | Rests on arithmetic, on an API known from documentation or memory, or on a reading. It stays inferred until new evidence arrives |
| Unresolved | Not established |
| Same code | The x86 of `spel.dat` lifted one to one to wasm ([recompiler.md](recompiler.md)). A real argument for in-race logic, not a comparison. It does not cover the functions in `tools/recomp/replacements.py`, x87 (f64 here), the clocks (one virtual clock, fixed tick of 1/60 s), anything the host answers, rendering or audio. It does not apply to the menu, which is a hand rewrite |
| Implemented, verified | Kept apart. This file says where a system is implemented and which check ran on it. Status per feature is in [feature-parity.md](feature-parity.md). A run that ends without an error does not establish parity |

Addresses: `FUN_` and `0x` are `spel.dat`, `M:` is `menu.exe`, `L:` is `A2Racer4.exe`. Note names such as `sim-timing.md` C1 are in [`research/`](research/). E0..E9 are `etappe0..9`. E9 came with the track update, and a row that lists etappes covers E0..E8 unless it names E9. wu = world unit, 0.1 m. PSI = one Ipion step.

These checks are the only verification cited, on E0 (Amsterdam) unless the row says otherwise, in headless Chromium 145 on an AMD Radeon RX 6700 XT through ANGLE Vulkan, or in Node where stated. Builds and dates: [validation.md](validation.md). The original's half of reference-wine ran under Wine, and of reference-86box on an emulated machine. Sound by state only, never by ear. No real phone or tablet, no real gamepad, no other browser engine. A check covers only what it says.

## The engine

A C++ engine of Davilex's own, MSVC 6, source paths `C:\Work\A2IV\...`. Nothing here assumes it is shared with another Davilex game. Inferred from INI comments: lineage from an older game ("Old (Autobahn Raser I)", "New (A2 Racer II)").

| Part | What it is | Port |
|---|---|---|
| Launcher, menu | `A2Racer4.exe` alternates menu and race. `menu.exe`: Delphi 5, 45 form resources, archive I/O through `rsc.dll` | `source/app.js`; hand port in `source/menu/` |
| Race | `spel.dat`, a PE32 with a `.dat` name, over 120 `.cpp` files named by `__FILE__` strings. Physics: Ipion through `DaviIpionSupport`. Scripts: DaviScript, one compiled `bonus.dso`, 190 script functions. Input: InputLib on DirectInput | Recompiled to `public/game/spel.wasm`, `tools/recomp/`. `bonus.dso` runs unchanged |
| Renderer | Own code on DirectDraw and Direct3D 5 immediate mode, `IDirect3DDevice2` | Calls answered by `source/host/directx.js`, drawn by `source/render/d3d-renderer.js` through Three.js |
| Sound | Secondary DirectSound buffers, one thread, no 3D object, no streaming | Calls answered by `source/host/directx.js`, played by `source/audio/game-audio.js` on Web Audio |
| Data | `.d3d` models; tracks `.cmp .dmp .pmp .rmp .omp .pth`; `VDYNS.DAT`; archives `rcs.img/ind`, `rc.img/ind`; INI | Unchanged files through `source/host/vfs.js`, `source/host/game-files.js` |

## The timing decision

The port runs `handle_game` at a fixed 60 ticks per second and draws at the display's rate. 60 is not the original's rate: the original has none. The brief asks that the choice rest on the original's behaviour, so this section gives the evidence on both sides. Material: [behavior/sim-timing.md](behavior/sim-timing.md#timing-frame-rate-dependence-and-the-fixed-tick), `research/sim-timing.md`.

### What the original does

1. **Physics has a fixed step.** `FUN_004a6a10`, `FUN_004a3960`, `FUN_004f7af0` set env+0xC0 to `(double)0.015151516f`: 66 PSIs per second at any tick rate. `FUN_004aa0c0` smooths `dt` once more (plain mean for 50 ticks, then 49/50) and `FUN_0050bd80` pops PSI events until the sum is reached. With `dt` at most 0.1 that is at most 7 PSIs per tick, 1.1 at 60 Hz. Matrices are extrapolated to env time, so the pose moves on every tick even if no PSI ran. Confirmed.
2. **The main loop runs free.** `WinMain` `FUN_00458270` runs one `FUN_0044cb80` per drawn frame. Step 14 draws, step 15 steps physics, step 22 presents with `Flip(NULL, DDFLIP_WAIT)`, the only pacing; `Sleep` is not imported, `WAITVBL=0` ships. Input of tick N reaches the car in step 3, physics in step 15, the screen in step 14 of tick N+1. Confirmed. Measured, see below: with nothing limiting it, 317 to 393 ticks per second. Inferred (`sim-timing.md` I2): it runs between about 15 FPS and the refresh rate, and no rate is designed in.
3. **`dt` comes from a ring.** `FUN_004a6700`: 4 f32 samples, `dt = .5 b[i] + .25 b[i-1] + .125 b[i-2] + .125 b[i-3]`, stored f32 after each term. `FUN_004a6800` returns 0.1 when the field is 0 or above 0.1. 208 call sites in 114 functions, by first FPU operation: 106 `FMUL` (rate times `dt`), 46 `FADD` (timers), 24 `FDIVR` (`K/dt`), 32 others. Confirmed. Measured at 60 ticks per second on a clean clock: 0.1, 0.1, 0.1, 0.0158, 0.0185, 0.0166, then 0.0160 to 0.0173.
4. **Race clocks do not follow `dt`.** 18 `GetTickCount` slots and 34 functions with ms thresholds. Below 10 FPS game time slows while these keep real time. Confirmed.

### The original's rendering behaviour, measured

The brief asks to measure the original's rendering behaviour and to determine its simulation timing separately, with no assumed frame cap and no assumption that the two run at the same rate. reference-wine ran the original race program and read its memory per tick. ### What the 4-entry clock ring keeps

`0x004A6700` is replaced by `hook!updateClock` in `Race.instantiate` (`source/host/race.js`). It keeps the ring and its weights, writes `time` from the virtual clock, and feeds exactly one tick per sample after the first two. So:

- A steady ring alternates the last bit of `dt`, `0x3c888888` and `0x3c888889`. `dt*300` falls just under and just over 5, and the truncating gas step mixes +4 and +5: 23 ticks to full gas, against 21 to 23 measured in the original. An exact `dt` gave 19. This is deliberate and measured, not noise. The rounding noise of a float counter itself is left out.
- After a dialog `FUN_004a6840` runs as shipped: the ring reads 0.1 again, and the next ticks read 0.0583, 0.0375, 0.0271, 0.0167 s, as the original's code gives (arithmetic, not measured).
- At the start the first ring sample is the clock's value at init. The second is `INIT_TO_FIRST_TICK` = 8.4 ms: `L`, the time from clock init to the first tick, measured at 8.42 ms (7.86 to 8.94, 15 starts) on that machine. Ticks 1 to 3 are capped on any machine up for more than a second (Confirmed). Tick 4 is capped only if `0.875 T + 0.125 L` is above 0.1, which needs `L` above about 0.68 s at 60 Hz. So 3 capped ticks, and tick 4 not capped, as measured: `dt` 0.1, 0.1, 0.1, 0.0156, 0.0167 against 0.1, 0.1, 0.1, 0.0158, 0.0185. Physics delta on ticks 4, 5, 6: 0.0789, 0.0665, 0.0582 against 0.0790, 0.0669, 0.0585. At GO physics has run 5.87 s against 5.83 to 5.86 s, a lead over the wall clock of 1.17 s against 1.18 s. By arithmetic the lead is 1.16 s with 3 capped ticks and 1.47 s with 4.
- Restoring the ring in place of `dt` = T from the first tick changed which launch regime the fixed-seed runs land in, not the physics (traced). The clock changes after reference-wine did the same.

reference-wine reads `dt`, the raw sample and the physics delta per tick in both. Same code does not apply to this hook.

### Traffic share

`FUN_00428950` (traffic) and `FUN_00415e40` (path vehicles) push per tick with no `dt`, with mass `m = 1/(obj+0xB0)` from the `FDIVR` at `0x42898f` and `0x416002`. Thrust goes through the same actuator as turbo, so it lands once per tick at full strength up to 66 Hz. The owner measured that traffic lifts its nose at high rates (mean / highest forward y after a start: 0.19 / 0.30 at 30 FPS, 0.51 / 0.74 at 60, 0.69 / 0.72 at 66, 0.13 / 0.19 at 240) and patched `traffic_mass` to `m * min(1, dt*25)`. The 25 is the factor in the game's own turbo formula.

The port does the same: `PATCHES` in `tools/recomp/replacements.py` point the two operands at `TRAFFIC_SHARE` `0x003F1000`, and `Race.instantiate` fills it with `min(1, tick*25)`, 0.41667. Every force in those two functions scales with it, one whole push per 1/25 s. This follows the owner's patched game, not unpatched 1.01, and is recorded as a difference. check-traffic, Amsterdam, 110 s of a bot, mean / highest:

| Rate | Port, whole pushes | Owner, original under Wine | Port, with the share | Owner, patched game |
|---|---|---|---|---|
| 60 | 0.295 / 0.742, 24 starts | 0.51 / 0.74 | 0.087 / 0.208, 15 starts | 0.08 / 0.18 |
| 30 | 0.102 / 0.327, 17 starts | 0.19 / 0.30 | 0.064 / 0.193, 17 starts | 0.11 / 0.19 |

The highest values agree within 0.03 in all four cells. The means are over more starts of more kinds than the owner's 3 to 7, so they are not comparable. reference-wine could not make this measure on the original: a car waiting at the start sees 0 or 1 traffic starts in 31 s. ### Rendering rate and interpolation

`RaceRunner.frame` in `source/race-runner.js` runs ticks by accumulated time, so the display rate does not set game speed. No cap on rendering. Elapsed time is capped at 0.25 s per frame and at most 6 ticks run per frame, the rest dropped. Every tick runs the render path, because effects update there; `captureLevel` keeps only what the last two ticks of a frame need.

`blendPalette` in `source/render/d3d-renderer.js` blends world matrices, moving vertices with equal vertex count and the view matrix between the last two ticks, alpha `acc / tick`. Up to one tick (16.7 ms) of added latency. Cut when a matrix, a draw's first vertex or the camera eye moves more than 30 wu in a tick. Not blended: projection, HUD, `gfx_wolk`, `gfx_bwlk`, all particles, strips whose vertex count changed. Above 60 Hz those step at 60 Hz. Under a dialog and at the end of a race `present(1)` shows the key tick's own frame.

What that costs, on purpose. After the first 3 ticks `dt` is about 1/60 whatever the device does, so the FPS gates cannot fire (re-placement below 15, spawns at 12, wipes below 10), and the view distance governor never fires because it needs state 0; view distance and effects stay full on a slow device. Falling behind slows game time, as the `dt` cap does in the original, but `GetTickCount` timers slow with it instead of keeping real time. Focus loss, a hidden tab and the open settings panel stop every clock, where the original's timers keep running while the window is inactive. The flitser's white frame lasts one tick, shorter than on a period machine at 25 to 30 FPS.

What was checked is port against port. repeat-trace: checksums over all 485 physics bodies equal at 71 samples at 60 and 30 FPS and under 8x CPU throttle, always 60 ticks, and the player's position and speed differ by 0. benchmark at the mobile profile: frame ms p50 16.7, p95 16.7, p99 16.8, max 16.8; tick mean 7.19, p99 9.8, max 14.5; present mean 0.65, max 2.5; so the 6-tick cap and dropped ticks were not exercised. check-flow at speed=8 ran ticks at `captureLevel` 0 without measuring them. Fix checks with a 144 Hz timer in place of `requestAnimationFrame`: 4031 presents, none with the view unblended; camera switches still cut. No real display above 60 Hz was used, and interpolation quality was not judged by eye.

## Findings a continuing developer must know

1. **The player's car has launch regimes, more than two.** `FUN_00500820` stops movement checks for a sim unit once any core is above 1 m/s, so the state a core holds at that moment stays. State 2 adds 0.1 to its rotation and speed damping factors (`FUN_004f3d20`). Chassis and each wheel core latch separately, all within 0.17 s of the gas. Record 11, speed after gas in m/s at 1, 4 and 8 s, original / port, state written chassis first. 11111: 6.65 / 6.67, 20.67 / 20.69, 27.73 / 27.72. 22222: 6.35 / 6.37, 17.33 / 17.34, 23.71 / 23.72, still rising. 21111: 6.46 / 6.59, 19.13 / 19.22, 27.73 / 27.68. 12222: 6.45 / 6.53, 18.61 / 18.65, 26.72 / 26.77. Mixed ones such as 21122 only in the port. The moment of the gas does not decide it in the original: one key script six times gave 22222, 11111, 22222, 11111, 21111, 11111. The port is repeatable, and it changes regime when the moment moves by a few ticks, so a tick number in the port is not a constant: 81 moments gave 11111 38, 22222 21, 21111 14, 12222 5, 21122 3. So one speed figure for "acceleration" means nothing without the state, and any comparison of two runs must first compare it. check-race-ui asserts no regime: at 4 s it read 20.64 m/s on the keyboard, 17.28 on the touch wheel and 17.32 on the stand-in pad. Confirmed from code, and measured under Wine. Unresolved: what decides the state, and whether the shares are the same.
2. **Turbo force is normalised.** `FUN_004a5ce0` rotates the stored actuator vector, then `FUN_004f9680` at `0x4a5d9c` normalises it in place. So one PSI gets the full value and every later PSI length 1, until the next set. The set has `dt` in it, so force is `25 m (0.025 abs(v) + 0.5)` whatever the tick rate up to 66 Hz. After the last set about 66 N stays. `m` is `car_cfg` Mass, not the body's mass. Three notes had this wrong.
3. **Wall-clock timers run during dialogs.** `FUN_0044ca80` stops only clocks 0, 3, 0xB and six racer clocks. Slots 1, 5, 7, 0xF, 0x10, 0x11 and all stamps run on, and `time` jumps by the pause length at the reset. So invulnerability, freeze and fast-forward run out in a pause, and pickups fade and respawn. `Race.tick` advances the clock in its pause branch to keep this. Do not "fix" it.
4. **There is no arrest and no reverse gear.** State 5 has no writer, `RacerCloseAndStopped` and `ArrestReady` have no call or pointer, so contact with police is physics and damage only. `CarBackward` is brake; reverse tops out at the same wheel limit as forward (measured: -27.79 to -27.91 m/s steady).
5. **Damage changes the look and the score, not the handling.** It bends and drops parts and hides sub-objects; nothing reads it for engine, grip or steering. Numeric damage is 0 at each start; only `DAMAGE_MESH` carries over, across modes, characters and players.
6. **Gears change only torque.** `speed` in `FUN_004a2f70` is the sum of four wheels, not their mean, so top gear is reached from about 11 km/h (the log shows gear index 4 at every sample from 1 s; measured: index 4 after 0.27 to 0.33 s of gas in the original, 0.25 to 0.32 s in the port). Engine sound follows speed only.
7. **Timer 11 ends a race only in mode 1.** `FUN_0044c8c0` tests the table at `0x6fa61c`. On other tracks it runs out at 110 s and `FUN_0044b1c0` writes `out_of_time`, so `FINISHED=1` with `Out_Of_Time=1` is normal there, as check-flow's 593 s race wrote. The menu tests `FINISHED` first. Confirmed from code; not traced on that race.
8. **Shipped data switches much code off.** No chunk has trigger 2, so `QUICK SERVICE` never occurs. No chunk or waypoint has speed trigger 4, 5, 6 or 8, so the flitser limit is always 70 km/h. No `.pth` of type 1, so the start camera path never runs. Checkpoints exist only on E1, E3, E4. A function's presence proves nothing: `FUN_00431320` (trailer), the raycast car `FUN_004a5e70`, `PHYS%d.DAT` and the manual shift `0x403020` are dead.
9. **Cops take the player's upgrades.** `FUN_00423a50`, `FUN_0041e450` build them at the player's levels. AI racers run level 0 with `MaxSpeedPenalty` 90, 120, 200 % and `MaxRPMPenalty` 115, 80, 50 %. Both rubber bands apply only in leagues 0 and 1.
10. **Visibility is a chunk window.** No frustum test, distance test or LOD, and nothing culls by aspect, which is why wide views work without touching game code. 55 degree test: the end of the window can show earlier on very wide shapes.
11. **The HUD is 3D.** Each part is a mesh with one world matrix; it draws before skid marks, smoke and flag, and stays on top by depth. Rotation tables have 4096 entries at run time, not the 1024 in the image.
12. **Two compatibility faults are not game behaviour.** `FUN_004a6700` keeps seconds since boot in an f32, so at long uptimes the world slows or stops (owner: step values -0.0726 to 0.1109 at a faked 30 days; measured at 31 h of uptime: `dt` 0.0141 to 0.0201 at 60 ticks per second against 0.0160 to 0.0173 clean, raw steps down to -0.0016 at about 360); the virtual clock removes it. `FUN_004bc0f0` fills a 1024-entry stack array with no bound check: black screen or crash above about 128 MB of video memory; the host stops it at 16 MiB.
13. **Tour rules have edges the code keeps.** A finished Tour race clears all tune-up flags. A chase advances without the equality check, so a replay moves on. Winning resets nothing. +2500 on every win, replays too.
14. **Other etappes may not behave as E0 does.** Traffic stops for red lights only on E0, chases and the Supercop are only on E1, E3, E4, cops are not on E5, E6, E7, `VEHICLE13..17` only on E6, highway rules only on E8. None of that has run. E9 is the only track with `BRITISH=1`: it drives on the left, seen only on the launch check's screenshots.
15. **The gas pedal needs a tick slower than 1/300 s.** `FUN_0046f2a0` truncates `gas + dt*300`, so at about 360 ticks per second on a clean clock it hardly rises: highest speed 1.25 to 12.66 m/s in 12 s, measured under Wine. At 60 ticks `dt*300` lies around 5, and clock noise mixes +4 and +5: 21 to 23 ticks to full gas. The port's `dt` alternates its last bit for that reason, 23 ticks. Do not "clean" it to an exact 1/60: gas then takes 19 ticks, and speed at 1 s runs up to +2.64% ahead of the original, against +2.05% now.
16. **A race starts with 3 capped ticks, not 4.** The load runs before clock init, so what enters the ring is the clock's value at init and 8.42 ms, measured on one fast machine under Wine. `dt` is 0.1, 0.1, 0.1, then 0.0158 in the original and 0.0156 in the port. Physics leads the wall clock by about 1.18 s at GO. Tick 4 would cap only above about 0.68 s at 60 ticks; whether a slow machine reached that is Unresolved.
17. **The car update's `game.ini` comes from the developers' machine.** It has `Nrlaps=1`, `etappe=8`, `car=7`, `money=1330`, the tune-ups on, results of a race of theirs, and a key the disc's copy lacks, `[GFX OPTIONS] OVERLAYELEMENTS = 15`. The menu writes the race keys before every race and the race writes the results, so a player does not see them. Anything that starts a race without the menu must pin them: `pinRace` in `source/host/race-setup.js`. `FUN_00449b30` reads the key into `0x5ab3c0`, and the mask counts only when `0x712784 == 1`, through `CM_KEYB_5`: at 15 that debug view keeps elements 1, 2, 4, 8 instead of hiding everything as at 0 (`hud-overlay.md`). The port reads 15 like the original. Not exercised in any check.
18. **The 8-bit path's look cannot be read from the code alone.** The game hands vertex colours and alpha to the Ramp device, and what they become is decided inside `D3DRAMP.DLL`. The static notes read them as vertex colour, opaque, alpha ignored. Frames of the real rasteriser showed otherwise, and both rules in the port were measured: palette index `255 - floor(blue / 17)` on untextured draws, and a stipple by the first vertex's alpha, `16 * T < alpha` on a 4x4 matrix. So smoke is sparse dark dots, and skid marks dense hatching when new. Confirmed for the values read, on one emulated machine. Inferred: why these palette indices, and the thresholds no frame was read at. So for how this path looks go by [`research/render-8bit.md`](research/render-8bit.md) and a frame from `tools/reference-86box/`, not by reading the code or the `8bit-*.md` notes.

That is a mean, not a pixel comparison. Of the menu only the intro and the CD dialog were seen, in the Wine runs. Nothing was heard.
